# Prompt para o Replit — Criação e População do Banco de Dados

Quero que você crie, configure e popule o banco de dados da aplicação de **plantões médicos**, respeitando rigorosamente o modelo conceitual definido.

> **IMPORTANTE:** não simplifique o modelo, não remova entidades e não transforme as informações em uma única tabela. Respeite as entidades, atributos, chaves primárias, chaves estrangeiras, cardinalidades e relacionamentos descritos abaixo.

Utilize um **banco de dados relacional, preferencialmente PostgreSQL**.

---

# 1. Contexto da aplicação

A aplicação conecta **Hospitais/Clínicas** que possuem plantões disponíveis com **Médicos** interessados nesses plantões.

O fluxo principal é:

1. Um Hospital/Clínica é cadastrado.
2. O Hospital/Clínica publica um ou vários Plantões.
3. Médicos são cadastrados na plataforma.
4. Um Médico pode se candidatar a diferentes Plantões.
5. Cada candidatura deve ser registrada na entidade `candidatura`.
6. Um Plantão pode receber várias candidaturas.
7. Cada candidatura pertence obrigatoriamente a:
   - exatamente 1 Plantão;
   - exatamente 1 Médico.

---

# 2. Entidades do banco de dados

## 2.1. Tabela `hospital`

Representa os hospitais ou clínicas responsáveis pela publicação dos plantões.

### Campos

| Campo | Tipo | Regra |
|---|---|---|
| `idhospital` | integer | PRIMARY KEY, auto increment |
| `hospitalnome` | varchar/text | NOT NULL |
| `cnpjhospital` | varchar | NOT NULL, UNIQUE |
| `cidadehospital` | varchar/text | NOT NULL |

### Relacionamento

- Um Hospital/Clínica pode publicar **0 a N Plantões**.
- Cada Plantão pertence obrigatoriamente a **1 Hospital/Clínica**.

---

## 2.2. Tabela `plantao`

Representa os plantões médicos publicados.

### Campos

| Campo | Tipo | Regra |
|---|---|---|
| `idplantao` | integer | PRIMARY KEY, auto increment |
| `localizacaoplantao` | varchar/text | NOT NULL |
| `dataplantao` | date/timestamp | NOT NULL |
| `valorplantao` | numeric(10,2) | NOT NULL, valor >= 0 |
| `especialidadeplantao` | varchar/text | NOT NULL |
| `statusplantao` | varchar/text | NOT NULL |
| `idhospital` | integer | NOT NULL, FOREIGN KEY |

### Foreign Key

`idhospital` deve referenciar:

`hospital(idhospital)`

### Relacionamentos

- Um Hospital possui **0:N Plantões**.
- Cada Plantão possui **1:1 Hospital**.
- Um Plantão pode receber **0:N Candidaturas**.

---

## 2.3. Tabela `medico`

Representa os médicos cadastrados na plataforma.

### Campos

| Campo | Tipo | Regra |
|---|---|---|
| `idmedico` | integer | PRIMARY KEY, auto increment |
| `nome` | varchar/text | NOT NULL |
| `especialidade` | varchar/text | NOT NULL |
| `crm` | varchar | NOT NULL, UNIQUE |
| `cidade` | varchar/text | NOT NULL |

### Relacionamento

- Um Médico pode realizar **0:N Candidaturas**.
- Cada Candidatura pertence obrigatoriamente a **1 Médico**.

---

## 2.4. Tabela `candidatura`

Representa a candidatura realizada por um médico para determinado plantão.

### Campos

| Campo | Tipo | Regra |
|---|---|---|
| `idcandidatura` | integer | PRIMARY KEY, auto increment |
| `data_candidatura` | timestamp/date | NOT NULL |
| `status` | varchar/text | NOT NULL |
| `idplantao` | integer | NOT NULL, FOREIGN KEY |
| `idmedico` | integer | NOT NULL, FOREIGN KEY |

### Foreign Keys

`idplantao` deve referenciar:

`plantao(idplantao)`

`idmedico` deve referenciar:

`medico(idmedico)`

### Relacionamentos

- Um Plantão pode possuir **0:N Candidaturas**.
- Cada Candidatura pertence a **1:1 Plantão**.
- Um Médico pode realizar **0:N Candidaturas**.
- Cada Candidatura é realizada por **1:1 Médico**.

Adicione também:

`UNIQUE(idplantao, idmedico)`

Isso deve impedir que o mesmo médico se candidate duas vezes ao mesmo plantão.

---

# 3. Cardinalidades obrigatórias

Respeite exatamente estas cardinalidades:

## Hospital → Plantão

- Hospital: `(0, N)`
- Plantão: `(1, 1)`

Representação:

`hospital 1:N plantao`

---

## Plantão → Candidatura

- Plantão: `(0, N)`
- Candidatura: `(1, 1)`

Representação:

`plantao 1:N candidatura`

---

## Médico → Candidatura

- Médico: `(0, N)`
- Candidatura: `(1, 1)`

Representação:

`medico 1:N candidatura`

---

# 4. Integridade referencial

Configure corretamente todas as Foreign Keys.

Preferencialmente:

### Plantão → Hospital

`plantao.idhospital`

REFERENCES `hospital(idhospital)`

`ON DELETE RESTRICT`

### Candidatura → Plantão

`candidatura.idplantao`

REFERENCES `plantao(idplantao)`

`ON DELETE CASCADE`

### Candidatura → Médico

`candidatura.idmedico`

REFERENCES `medico(idmedico)`

`ON DELETE CASCADE`

Não permita registros órfãos.

---

# 16. Integração com a aplicação

Depois de configurar o banco, ajuste o backend para utilizar os dados reais.

Não mantenha mocks quando as informações puderem ser buscadas diretamente do banco.

A aplicação deve funcionar assim:

- Hospitais → tabela `hospital`
- Médicos → tabela `medico`
- Plantões → tabela `plantao`
- Candidaturas → tabela `candidatura`

Os dados do Hospital responsável pelo Plantão devem ser obtidos pelo relacionamento:

`plantao.idhospital → hospital.idhospital`

As informações de candidatura devem utilizar:

`candidatura.idplantao → plantao.idplantao`

e:

`candidatura.idmedico → medico.idmedico`
